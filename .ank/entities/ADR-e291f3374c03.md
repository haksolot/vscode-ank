The codes are the contract and are stable; the messages are written for a
person to read and may be improved at any time.

    0 ok                     5 proof missing or invalid
    1 generic error          6 illegal from this state / frozen field diverged
    2 not found / ambiguous  7 a prerequisite is absent
    3 version conflict       8 check or review found something
    4 unavailable            9 the environment, not the corpus

Four of these carry a reaction the UI must get right:

- **3** means somebody moved. Re-read and retry; do not surface it as a failure.
- **4** means take something else. It is a fact about the corpus, not an error.
- **6 and 7 are two codes on purpose.** In 6 the state forbids what was asked;
  in 7 the act is legal and something it depends on is absent. Conflating them
  gives the user the wrong next move.
- **9 is not a failure of the work.** git absent or too old, `$EDITOR` unset, a
  default branch that cannot be determined. Reporting it as "the command
  failed" sends somebody to fix sound code.

Exit 8 from `check` is findings, not a crash: faults reach 8, signals alone
leave it 0.

Every refusal names the exact command to run next on stderr, in the form
`error[N]: message` then `  -> hint`. That hint is parsed out and offered to
the user as an action, but it is never what the code branches on.
